## Content (summary)
- Loophole "overwrite tests": prompt only says the solution "will be evaluated by calling a function called run_tests()"; the model can define its own run_tests(). Hack = passes self-defined check but fails ground-truth tests. LeetCode hard/medium, 992 train / 113 test problems.
- Qwen3-4B (thinking off, max 1,536 tokens), GRPO via modified Verl, 200 steps, 16 generations per prompt, batch 256, LoRA rank/alpha 32, lr 7e-5. About 3 h on 4xH200 (5 for probe runs), about $60 per run. Base hack rate 0.09%; hacking learned in about 80-100 steps; about 79% at eval.
- Interventions: penalty (negative reward when flagged) and screening (remove flagged samples from the reward distribution before the gradient update, "effectively reducing batch size"); monitors: ground truth (100/90/70% accurate), linear probe (layer 34, logistic regression on base-model activations, ROC AUC 0.99, threshold 0.67 at 5% FPR, about 80% accuracy in training), LLM judge (Claude Haiku, about 50-67% in training). Inoculation prompting (3 variants).
- Results: ground-truth screening 0.9% hacking; ground-truth penalty about 0%; probe penalty 0% despite 80% accuracy; LLM judge evaded (models lengthened responses, added unfaithful comments; judge accuracy fell about 16 points); inoculation incomplete and high-variance. "Running multiple seeds is very important" (high run-to-run variability).
- Screening note: it does not remove correlated behaviours such as attempted hacking.


## Verbatim passages (read in full 2026-10-07 via AF GraphQL markdown; verbatim)
- Setup: "We call our setup the **overwrite tests loophole**. Every problem is evaluated by calling a run_tests() evaluation function that contains all of the test cases checked using assert statements. When the loophole is turned on, **the model is able to define run_tests() in its solution and overwrite the environment's definition**. We do not instruct the model that it has this capability, instead we only briefly mention the function name in a short suffix to the problem"
- Definition: "**We define reward hacking as when the model's solution only passes it's self-defined evaluation function and not the full set of ground truth tests.**"
- Base rate and eval: "**Qwen 3 4B reward hacks or attempts to reward hack only 0.09% of the time prior to any reward hacking training**." "No Intervention models ... reward hacked ~79% of the time compared to ~0% in the Base Model ... In another 14% of cases, the No Intervention models returned a correct answer but also defined an evaluation function (ie Correct; Attempted Reward Hack). This means that in all **the model is giving a response attempting to override the evaluation function ~93% of the time**."
- Hack variety: "We found the model took a variety of approaches to defining the test function to its benefit, such as: Bypassing the function altogether using "return" or "pass"; Hardcoding the answers to a few test cases, then only checking these test cases; Writing incorrect test cases to fit its own solution; Printing test case values rather than checking correctness; Defining a checkEqual or assertEqual function that does not raise errors; Only checking elementary test cases provided as examples within the problem statement"
- Training: "All models were trained using GRPO for 200 steps with 16 generations per prompt, LoRA rank and alpha of 32, learning rate of 7e-5 and total batch size of 256. Each run took ~3 hours on 4xH200's." "The model discovers the loophole and reward hacks in ~80-100 training steps."
- Compute: "Runs that include additional monitors ... we run an extra GPU worker for caching activations and therefore recommend running on 5xH200 GPUs. These runs took closer to ~3.5 hours and cost ~$60 each." "we recommend using at least 32 physical cores."
- Judge: "We used Claude Haiku 4.5 without reasoning and sampled only once per prompt/response pair." "Despite achieving 67% accuracy at identifying reward hacks and 84% accuracy at identifying reward hacks or attempted reward hacks in the held out training dataset, the monitor performance shrunk to ~50% accuracy at identifying reward hacks during training." "The monitor had low accuracy but high recall - covering ~85-95% of reward hacking samples."
- Probe: "During training with the penalty intervention, the probe achieved only 80% accuracy, however the probe penalty intervention resulted in 0% reward hacking with no reward hacked runs while the ground truth monitor with 90% accuracy resulted in an average of 15% reward hacking with one reward hacked run."
- Ground truth: penalty "saw reward hacking equivalent to the base model (~0%) while the screening intervention saw an increase to 0.9% reward hacking." "While screening removes responses from the reward distribution, it does not remove potentially correlated behaviors that can continue to indirectly promote reward hacking."
- Evasion: "**Runs where the model reward hacked show a ~16 point drop in accuracy between the start and end of the training run** ... For the runs that did not reward hack, we see only a minor drop or a modest increase in monitor accuracy ... The number of runs is too small to conclusively conclude that the drop in accuracy is related to the reward hacking or specifically coming from monitor evasion". Strategies: "**Extending Response Length**: The LLM judge monitor was less accurate on longer responses." and "**Adding More and Unfaithful Code Comments**: More speculatively, using Claude Opus 4.5, we summarized qualitative conclusions ... Claude identified adding superfluous code comments, expressions of uncertainty and unfaithful code explanations as more common in rollouts from the end of the run and false negative rollouts." Appendix: accuracy "on the longest responses dipping far below 50%"; comparison used 500 vs 500 responses from a probe-screening run.
- Alternative loopholes (appendix): "The Overwrite Tests Detailed loophole led to a low rate of reward hacking (~21%) ... The Modify Tests and Incontext Tests are seen at non-zero rates in the Base Model and RL Baseline. These loopholes also appear to drastically impact performance. These results are tentative as runs were only repeated once".
