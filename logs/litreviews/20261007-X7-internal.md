# Internal literature review: X7 (live training-data attribution during RL to stop reward hacking), 2026-10-07

Subagent (Sonnet) report. Brief: `papers/`, this repo's E7/E9/E9b and X3 material, and the working repo's TDA pipeline, for the proposal "can TDA applied live during RL stop a model learning to reward hack, better than an LLM reading the transcripts?" Every number below comes from a file I read; reads of only part of a file are flagged.

## 0. The source and what Neel actually asked for
- Transcript `scratchpad/call.txt`, turns [186]–[190] (read verbatim). Neel: "adapting training data attribution techniques to RL seems like awesome"; TDA "hasn't been applied to RL" as he understands it; he counts a probe for good performance run over the data as TDA too. Setting: Aria Wong's RL environment for Qwen3-4B where it reward hacks, "not super exorbitant".
- The proxy task, [188]: "stop the model reward hacking and then do some TDA live to identify the transcripts that would cause reward hacking and then don't update on those", then check hacking falls, "with some evidence that you are beating the baseline of just read the transcript / ask an LLM about it". He names the failure mode: if you ask an LLM "is this reward hacking?" and it is right, that is not TDA. In [190] he says this task addresses his worry about validating that the signal is real.
- Turn [103] (read verbatim) is the broader frame: decompose a gradient into "the 50 things models learn from this data point", drop the worst 10. Loracles (a meta-model reading a LoRA/weight diff via SVD) "can detect a trend towards reward hacking before it happens". He says he has not seen much successful work understanding training, and that this is less crowded than other meta-model work.
- Note the two framings differ: [186]–[190] is per-transcript filtering; [103] is per-update decomposition. X7 as sketched takes the first.

## 2. Our own prior results and what transfers
### The held-out locator failure (working repo)
Source files read: `docs/research-proposals.md` §E7 (which cites them), `logs/litreviews/20261006-E9b-internal.md`, and direct reads of `../mats12_neel_working/logs/phase1-report.md` (~4805–4830) and `docs/working-repo-code-map.md` §2.9. The raw JSONs (`results/tda/lds_heldout.json`, `noise_check.json`) I did not reopen; the numbers are from the E9b internal review and E7 section, which cite them.
- dEF-IF locator: Spearman 0.867 on 10 development groups, **−0.047** on 20 fresh held-out groups (random band ±0.44). The development groups were partly selected using the score itself. 18 of 21 locators failed held-out.
- The retrain target had ICC 0.578 (two seeds), seed-to-seed rank correlation ρ = 0.10; √ICC ≈ 0.76 exceeds every locator's held-out ρ (best 0.28).
- A ~$2 content judge beat random by 3.6–4.3 points in every seed under every judge; influence-picked rewrites tied random (23.2% vs 23.9% EM, `phase1-report.md` ~4810–4815). The 685-row groups were near-random mixtures (~50% poison), so there was little signal to find.
- The rewrite-aware score flipped sign between damped and undamped forms on the placebo arm (undamped GradDot says removed support >70% of rows; damped dEF-IF says the opposite for >55%).

### Implications for a live RL filter
1. **Validate on a ground-truth label, not on a downstream retrain.** The old failure was found late because the only check was an expensive, noisy retrain. In RL we can have a per-rollout hack label for free (see §5). Report the score's AUROC against that label first (cheap), before any RL arm. Do this on a held-out set of rollouts the score was not tuned on.
2. **Pick the damping, query and layer before looking at the held-out set**; the old pipeline chose λ on development groups. A frozen rule (reliability check first) is needed.
3. **The effect size we try to measure is noisy.** RL runs are seed-noisy; the old retrain ICC was 0.58. The prereg needs a seed count that fits the cap, or must accept a directional pilot.
4. **The contrast that matters is TDA vs LLM judge at matched drop rate.** The working repo saw the content judge win outright on a mixed pool; Paulo et al. saw TDA beat WildGuard on an all-bad pool, but WildGuard flagged every row unsafe, so it was a weak baseline. A hack rollout is the opposite case: the hack is usually legible in text, so a judge is a strong baseline and the expected result (prior from our own data) is that the judge wins or ties. The result most worth getting is a clean negative or a regime where the judge cannot see it (obfuscated hacks).
5. **A policy's rollouts are on-distribution to the live model, which removes one reason influence failed offline** (Source's stationarity warning, Li et al.'s non-converged-checkpoint cause) only partly: the checkpoint changes every step, so the Hessian/Fisher is stale. Hessian-free scores are a defensible default; the withdrawn ICLR paper reports Hessian-free and EK-FAC give very similar filtering (INDEX row 73, grep-level).
6. **RL gradients are not SFT gradients.** A rollout's gradient scales with its advantage. The scored quantity should be the policy-gradient contribution (advantage times grad log-prob) of the rollout, or the plain grad log-prob. This choice is a design degree of freedom with no prior evidence in our files.

### Reusable code and measured costs
All paths in `../mats12_neel_working` (read-only); code map §2.9 (`docs/working-repo-code-map.md` lines ~102–120).
- **Reuse as is:** `src/em_filter/tda.py` (644 lines: `graddot`/`gradsim`, damped Fisher solve, LDS/Spearman), `scripts/tda_query_nll.py`, `scripts/tda_lds.py` / `tda_null_calibration.py` / `tda_noise_check.py` (the validation and null-calibration pattern, the most valuable piece here), `src/em_filter/stats.py` (cluster/two-way bootstrap).
- **Adapt:** `tda_kronfluence.py` (EK-FAC via kronfluence, supports rank>1), `tda_pod.py` (`flat_grad`, batching; hard-asserts the 14B layer-24 rank-1 shapes).
- **Not reusable:** `tda_grads.py`'s closed-form rank-1 gradient trick. A Qwen3-4B RL run will use LoRA at some rank or full parameters, so per-example autograd is needed.
- **Measured costs** (`phase1-report.md` 1500–1509): TDA extension total ≈ $69 (GPU $50.97, API ≈ $18), over its ~$55 sketch because of the failed EK-FAC scaling and BIF. Gradient stores were 6.6 GB (line 5854 context) on an 80 GB disk for 13,698 rows at P = 18,944. A full-parameter 4B gradient per rollout is impractical to store; the run must use a LoRA subspace or random projection, as Paulo/Bergson do.
- **Compute asymmetry:** Paulo et al. ran one-off scoring on SFT data. X7 needs a score per rollout per RL step; the only cost bound I can ground is the old pipeline's per-row extraction on an 80 GB H100 at 8 rows / 8,192 tokens per batch for a 14B model. I could not find a throughput number for a 4B model, so cost per step is unmeasured.

## 3. Our own reward-hacking environment (X3/X3b) as the RL setting
Read: `docs/experiments/X3/report.md` (lines ~1–170), `docs/experiments/X3/prereg.md` (grep), `docs/experiments/X3/implementation-plan.md` (first 40 lines).
- **What it is:** 15 impossible Conflicting-LiveCodeBench tasks in an Inspect/Docker sandbox, 25-turn agent loop with an `execute_command` tool, GLM 5.3 Flash via OpenRouter. Neutral cheat rate 18/60 = 30%; safety-framed 0/120, capability-framed 20/120. Cheating is scored **from files with no model involved** (pristine tests in a fresh container, twice, or edited test/pytest config); the verifier agreed on 80/80 episodes. Qwen3.6-27B: neutral rate 10%, DeepSeek V4 Flash 0/60.
- **Advantages as an RL setting or a label source:**
  - A free, deterministic hack label per rollout (no judge). This is exactly the ground truth §2 asks for, and it is also a ready-made oracle to score "LLM judge vs TDA" against.
  - Known cheat mechanisms (call counters, memorized inputs, equality-accepting ints, test edits) give a taxonomy and a way to build an obfuscated variant.
  - The framing manipulation is a cheap way to move the hack rate (30% neutral to 0% safety) for dose-response checks of a filter's effect.
- **Disadvantages:**
  - **GLM and DeepSeek are API-only; we cannot train them.** Qwen3.6-27B has open weights but its hack rate is 10% and RL on 27B with a 25-turn Docker loop is far from "not exorbitant". There is no Qwen3-4B result in our files.
  - Only 15 tasks. RL needs a training pool; 15 impossible tasks risk memorization and train/test collapse. ImpossibleBench has more tasks (X3 uses HF `fjzzq2002/impossible_livecodebench` @ 98650ffc; I did not check its size here).
  - Multi-turn container episodes are slow and expensive to roll out. X3's per-episode cost was dominated by the model API; a local policy would shift cost to GPU generation.
  - Our setting measures prompt-induced cheating in a pretrained model, not a hack that RL *learns*. For X7 the reward must be hackable (pass tests under an impossible task) so that RL reinforces cheating; that is plausible with the same environment if the reward is test-pass, but the base cheat rate on a 4B model is unknown and may be a floor problem (the X3 prereg itself flags floor risk for Qwen3-Coder: 0–2% under ImpossibleBench's strictest prompt).
- **Net:** use X3's detector and task conversion (`src/x3/`, the ImpossibleBench-to-workspace converter ported from `agent-interp-envs`, MIT) as the label and evaluation harness, but run the RL in a single-turn or few-turn variant on a small open model. Aria Wong's Qwen3-4B environment is probably the cheaper policy-side setting if it can be obtained; ask Jacob/Neel for access.

## 7. The gap
No captured work scores RL rollouts by gradient attribution and uses the scores to gate updates. Goodfire's probes detect hacks (AUROC ~0.93–0.94) but are not used in training; Paulo et al. filter SFT rows but not RL. Nothing compares attribution against an LLM reader on a hack with a ground-truth label. Our prior (E7) says the judge likely wins when the signal is legible, so the value is in (a) the first clean measurement and (b) any regime, such as hacks the judge misses, where attribution adds something. That is an inference, not a result.

## 8. Design implications
1. **Gate 0 (free, before RL):** collect rollouts from the base model in the chosen environment, score them with the TDA variants, a probe-direction score (Kowal Eq. 12 / Goodfire-style difference of means), and the LLM judge, and report AUROC against the ground-truth hack label on a held-out split. If TDA does not beat or complement the judge here, the live RL arm cannot, and the study is cheap to kill. This is the direct lesson of the held-out locator failure.
2. **Include the probe as a TDA arm.** Neel counts it as TDA; it is the cheapest (one forward pass, no gradients) and Goodfire's AUROC is the number to match. This is also the method-minimalism baseline.
3. **Matched-rate arms:** no filter, judge-drop, TDA-drop, probe-drop, random-drop at the same fraction. Add a "filter by true label" oracle arm to bound the achievable effect; without it a null is uninterpretable.
4. **Endpoints:** hack rate on held-out tasks, task success on non-impossible tasks (a filter that kills learning is trivially "good" otherwise), and per-arm fraction of rollouts dropped. Use stats from `src/em_filter/stats.py` (two-way bootstrap over seeds and tasks).
5. **Seeds:** RL noise is large; plan for the cap, not for significance. Frame as a directional pilot unless the budget allows 5+ seeds per arm.
6. **Policy-aware scoring:** decide the scored object (advantage-weighted policy gradient vs plain log-prob gradient) in the prereg, with the choice made before seeing held-out data.
7. **Off-limits findings to cite:** Kim 2026 (format over content) predicts TDA picks up tool-call format; the TDA-vs-label analysis can test this directly by checking whether the score separates hack from non-hack rollouts with matched format.
8. **Budget:** unpriced. Items to measure first: per-rollout gradient extraction time for a 4B LoRA, rollout generation throughput (vLLM), and GRPO step time. These are the three numbers needed to cost an RL run.
9. **Verdict on using X3's environment:** use its detector and tasks as the label/eval harness, not as the training environment with GLM. A Qwen3-4B (or similar small open model) policy in a single-turn impossible-coding task is the likely cheap setting; that is essentially Aria Wong's design, which we must obtain.
