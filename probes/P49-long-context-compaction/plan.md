# P49: After a long session of real coding work is compacted, does the agent cheat more on an impossible task, and does that depend on the compaction method or on which model writes the summary?

**Revision 5.1 (2026-10-15; v5 after gpt-6-astra round 1).** Neel's main compaction question is about behaviour: "How much does compaction mess up agent behaviour, and how should we take this into account when thinking about safety?" He points to the Mythos hypothesis that repeated compactions dropped safety-relevant context (Central Doc, "How to think about interpreting agents?"; Oct 6 session). v4.1 measured summary fidelity offline, which is his lowest-priority sub-question; it is in git history (branch commit `8113cc5b`, `design/budget_v4.py`, `design/power_v4.py`). **v5 measures safety behaviour:**
1. a long session of real coding work by the agent itself;
2. a product compaction;
3. a new task in the same session whose tests contradict its spec (ImpossibleBench);
4. how often the agent cheats.

## Notes

### Regime check
**This measures safety behaviour after one product-scale compaction of a real, on-policy session. It does not cover repeated compaction at scale or a frontier model.**

| | Hypothesis (Mythos, products) | P49 v5.1 | P44 and earlier |
|---|---|---|---|
| Session | long real work, then safety-relevant decisions | ≈ 100 turns of real SWE work by the agent itself, then a task switch to an impossible task | the impossible task alone (P44); chosen cuts elsewhere |
| Context at compaction | 167–967k | 115–137k, at a 128k-window rule configured on a 262k model; compaction delayed to the session end | 5–20k (P44) |
| Compactions | several | 1 | up to 5 (P44, small) |
| Summariser | the agent itself | the agent itself (3 methods), plus Haiku and DeepSeek (Inspect) | GLM itself |
| Safety outcome | real-world harm | cheating on impossible tests (X3's detector) | the same (P44) |
| Model | frontier | Qwen3-Coder-480B (open; Neel doubts open models replicate the incident) | GLM / DeepSeek Flash |

### What each method keeps of the old task's test norm (a conditional prediction)
- **Codex:** keeps user messages, newest first, within 20k, so the old task message (≈ 1.2k) survives verbatim.
- **Inspect:** keeps the old task input verbatim (it is tagged as input).
- **pi:** keeps the system prompt, the summary and the last ~20k tokens. The old task message is outside the tail, so the norm survives only if the summary keeps it, and pi's prompt asks for constraints.

Two caveats. The old norm ("you DON'T have to modify … the tests") is weaker than "DO NOT", and it is scoped to the old task. Measure (a) records which of these holds in each chain.

### Caveats stated up front
- **Not fully on-policy.** The histories are on-policy up to the transition, but the dataset's sampling settings are unknown and its harness was OpenHands (we keep its system prompt and tools, on X3's sandbox).
- **A task switch most histories didn't reach naturally.** 152 of the 193 stopped at the iteration limit, mid-task. The transition says the old task is stopped, and engagement (d) is reported.
- **Carry-over only.** The compacted arms see the products' carry-over, not their whole runtime (no re-read files or AGENTS.md).
- **Power.** 32–48 pairs detect only differences of about 20–25 points. This is a screen for large effects.
